Финансовые функции и RLS отдельно исполняются в восстановленном PostgreSQL через PGlite 0.5.10. Auth, Storage и cron в этом SQL-стенде представлены платформенными заглушками; это не проверка живого Supabase Auth и почтовой доставки. Сценарий responsive дополнительно читает публичный каталог, но не записывает товары. Письма сотрудникам не отправлялись, реальные продажи не создавались.

S1 — ПРАВА СОТРУДНИКОВ
Отмена продажи теперь требует владельца и свежего TOTP на сервере. Сотруднику не показывается кнопка отмены. Признак «на комиссии» нельзя менять сотруднику через прямой REST-запрос: триггер проверяет владельца при вставке с этим признаком и при его изменении. В интерфейсе переключатель отключён для сотрудника. Изменение сохраняется существующим журналом с автором и старым/новым значением.
Проверено: прямой запрос сотрудника запрещён; свежий владелец может изменить комиссию и отменить продажу; остаток и финансовая запись согласованы после отмены.
Файлы: admin-sales.js, admin.js, новая SQL-миграция.

S2 — ДЛИННАЯ СЕССИЯ И ФИНАНСЫ
Запрошенная сессия 30 дней сохранена. Финансовые RPC и управление доступами требуют подписанный Supabase JWT с aal2 и TOTP в amr не старше 15 минут, плюс активную серверную сессию. Обновление access token само по себе не продлевает свежесть TOTP. При отказе сервера появляется ввод кода; успешное подтверждение повторяет исходный запрос один раз. Черновик формы не теряется. Открытые финансовые поверхности скрываются и становятся inert после истечения подтверждения.
Проверено: неверный код, верный код, отмена, сохранение черновика, единственная запись после повтора, повторное открытие страницы, параллельные вкладки, отзыв/истечение сессии.
Остаточный риск: токен остаётся в localStorage, это не переход на BFF/HttpOnly. XSS в админке по-прежнему опасен; свежий MFA уменьшает окно риска для финансов, но не устраняет его полностью.
Файлы: admin-step-up.js, admin.js, admin.css, новая SQL-миграция.

S3 — TELEGRAM SDK
Обычный посетитель сайта не загружает Telegram SDK. Загрузка выполняется только при параметрах запуска Mini App. Поздняя загрузка не блокирует каталог. Добавлено пояснение в конфиденциальность на русском и английском.
Файлы: telegram-sdk.js, HTML обеих витрин, privacy.html, site-translations.js.

S4 — ДОСТОВЕРНОСТЬ КАНАЛА АНАЛИТИКИ
Сервер игнорирует заявленный браузером channel. Telegram определяется по проверенной HMAC-подписи initData и ограничению возраста запуска 24 часами. Дубли ключей, подмена и просроченные данные отклоняются. Профиль Telegram не записывается в таблицы аналитики.
Для отдельного app.juliproz.com добавлен серверный relay. Он получает доверенный IP от Vercel и подписывает IP, тело события и время; главный шлюз принимает эту подпись только в течение 60 секунд. Так запросы Mini App не попадают все под один IP прокси. Лимиты и дедупликация event_id остаются на сервере.
Нужна настройка: один новый случайный ANALYTICS_RELAY_SECRET, 64 hex-символа, в production окружениях главного сайта и Mini App. Значение нельзя класть в исходники или клиентский config.js.
Остаточный риск: анонимная веб-аналитика не является доказательством присутствия человека. Существующие лимиты ограничивают злоупотребления; валидный initData также может быть повторно использован в пределах срока, но не обходит лимиты и дедупликацию.
Файлы: analytics.js, server/analytics.cjs, server/analytics-relay.cjs, server/telegram-init-data.cjs, apps/telegram/api/analytics.js.

S5 — ВОСПРОИЗВОДИМАЯ СХЕМА
Добавлен schema-only baseline реально прочитанной схемы приложения от 16.10.2026: 29 таблиц, 79 исходных функций, ограничения, индексы, триггеры, RLS, права и default privileges. Данные пользователей, продаж, приглашений, секреты и история не экспортировались.
Единственный порядок развёртывания описан в supabase/schema/manifest.json. Старые разрозненные SQL-файлы сохранены как история и не должны повторно исполняться поверх baseline. Новая миграция добавляет исправления аудита. Для чистого Supabase есть bootstrap платформенных зависимостей, приватного бакета и retention cron. Первый владелец и секреты создаются отдельно.
Добавлены структурный снимок ожидаемой схемы и check-schema-drift.cjs. Для сравнения с живой базой нужно выполнить catalog.sql от роли владельца, сохранить JSON и сравнить. Скрипт сам не подключается к production. Текстовые различия между версиями PostgreSQL требуют проверки, а не автоматического принятия нового снимка.
CI восстанавливает схему, сравнивает снимок и выполняет SQL-проверки. PGlite — PostgreSQL 18; baseline содержит права MAINTAIN, доступные PostgreSQL 17+.
Файлы: supabase/schema/*, tests/schema/*, scripts/check-schema-drift.cjs, security workflow.

S6 — AUTH, ФОТОГРАФИИ, ПРИГЛАШЕНИЯ
Auth: через публичный Auth settings API подтверждены disable_signup=true и mailer_autoconfirm=false. Серверные password_min_length и password_hibp_enabled получить/изменить доступным API не удалось; панель Supabase не ответила. Эти два пункта НЕ отмечены как применённые. Подготовлены целевая конфигурация и скрипт проверки/применения через Management API. Требуются SUPABASE_ACCESS_TOKEN и SUPABASE_PROJECT_REF из менеджера секретов. Защита от утёкших паролей зависит от тарифа Supabase. Форма уже требует минимум 12 символов, но клиентская проверка не заменяет серверную.

Фото: товарные изображения больше не попадают в публичную статическую папку сборки. Серверный шлюз отдаёт файл только если текущий запрос видит ссылающийся товар через RLS. Для Supabase Storage добавлена Edge Function product-photo. Она проверяет публикацию/права и затем читает приватный оригинал сервисным ключом. Админка загружает фото с JWT и использует отзываемые blob URL в памяти, очищая их при выходе. Ленивые превью не запускают загрузку всего списка. Разрешённые CORS-источники сохраняют кадрирование фото на обеих витринах. URL в товарных карточках не переписываются в базе.
Нужны развёртывание шлюзов и фронтендов, затем перевод product-photos в private. До этого старый публичный бакет остаётся открытым. Старые deployment URL, чужие кеши и ранее скачанные копии нельзя отозвать одной сменой флага бакета. Фото, используемое также опубликованным товаром, остаётся доступным по этому опубликованному товару.

Приглашения: добавлены pending/sent/failed/unknown и отдельный operation ID. Наличие строки приглашения больше не означает, что письмо отправлено. Серверный service_role фиксирует результат отправки. Таймаут даёт unknown и предупреждение проверить почту перед повтором. Есть отдельные лимиты: 10 отправок/ожидающих/неопределённых исходов в час и 30 попыток в час. Подтверждённые ошибки не расходуют лимит успешных отправок, но входят в общий лимит попыток. Владение email и MFA проверяются отдельно от членства команды; отправка письма не выдаёт права администратора.
Файлы: supabase/rollout/auth-settings.json, scripts/check-auth-settings.cjs, server/product-photo.cjs, supabase/functions/product-photo/index.ts, admin-images.js, invite-store-admin/index.ts, новая миграция.

L1 — ДАТЫ
Единая бизнес-зона Europe/Kyiv для календаря загрузок, продаж, финансов и дневных группировок аналитики. Тонкая строка статистики остаётся скользящими 24 часами. Проверены полуночные границы и переходы летнего/зимнего времени. Исторические даты финансовых записей не переписаны.

L2 — ОСТАТКИ СТАРЫХ КАРТОЧЕК
stock_quantities=null означает одну вещь на всю карточку, включая товары под заказ. Нельзя добавить по одной единице каждого размера. Старая сохранённая корзина нормализуется. Продажа единственной вещи скрывает всю карточку. Явные остатки сохраняют свою логику; реальные остатки не придумываются и массово не изменяются.

L3 — АЛИАСЫ РАЗМЕРОВ
Сервер и интерфейс одинаково нормализуют кириллицу Х/М/С, 2XL/3XL, One Size и десятичную запятую. Продажа и повтор операции используют канонический размер. Если два старых ключа дают один размер, сервер отклоняет неоднозначность; редактор просит заполнить пустое количество вместо молчаливого сложения. Автоматической корректировки количества в существующих данных нет.

L4 — ПЛАН ЗАГРУЗОК
В план попадает первая публикация заполненной карточки: доступны бренд, название, раздел и допустимая обложка, available=true. Черновик не считается. Засчитывается сотруднику, который опубликовал, и в день публикации. Повторная публикация не увеличивает счётчик. Скрытая/проданная карточка сохраняется в учёте; удалённая отражается отдельно и не входит в выполненный план. Добавлен индекс для окна публикаций; подпись в админке обновлена.

L5 — ПАГИНАЦИЯ
Каталог читается по created_at DESC, id DESC с курсором вместо offset. Удаление или вставка перед текущей страницей не сдвигает следующую страницу. ID дедуплицируются, курсоры валидируются, чтение ограничено 20 страницами по 500 записей. При превышении лимита — явная ошибка, а не тихое обрезание. Проверен каталог 1100 строк с изменениями между страницами. Это не транзакционный снимок: новые записи, вставленные во время чтения, появятся при следующем обновлении.

L6 — ВЕС СБОРКИ
Публичная статическая часть около 2,2 MiB, Mini App около 2,1 MiB, админка около 19 MiB вместе с локальным фото-редактором. Каталог из 441 необходимого статического фото хранится отдельно в серверном пакете около 68 MiB. Эти 68 MiB по-прежнему входят в серверное развёртывание; это не размер загрузки первой страницы. Неиспользуемые исходные фото не попадают в public dist. Архив проверки содержит исходные материалы, поэтому значительно больше публичной статики.

1. Применить новую миграцию на отдельном Supabase-стенде; проверить реальные Auth, Storage, приглашение тестовому адресату и TOTP. Текущий baseline нельзя накатывать на существующую рабочую базу.
2. Настроить ANALYTICS_RELAY_SECRET в двух Vercel production-проектах. Для preview использовать отдельные секреты/стенд; production collector намеренно отклоняет preview.
3. Проверить Vercel-пакет: api/product-photo.js включает private-product-assets/**; Mini App разрешает импорт общих server-модулей за пределами apps/telegram. Это требует проверки конечного deployment bundle, локальная статическая сборка этого не доказывает.
4. На рабочей базе применить только 20261016144421_external_audit_security_and_logic.sql. Затем развернуть новую invite-store-admin и product-photo (verify_jwt=false для публичной функции фото; сама она проверяет доступ через RLS). Синхронно обновить сайт, Mini App и админку. На время окна обновления старое приглашение безопасно потребует обновить страницу.
5. После проверки шлюзов применить supabase/rollout/private-product-photos.sql. Проверить без входа: опубликованное фото 200, скрытое/несвязанное 404; с действующим админским JWT скрытое фото 200; после отзыва сессии доступ закрыт. Проверить превью, загрузку и редактор фото с настоящими заголовками CSP/CORS.
6. Применить auth-settings.json через check-auth-settings.cjs --apply и затем проверить без --apply. Скрипт выводит только результаты нужных проверок, не весь конфиг с секретами.
7. Получить catalog.sql с живой базы и проверить drift. Проверить канал/реальный IP Mini App в production, не передавая профиль в журнал аналитики.
8. Резервная копия базы и согласованный откат обязательны при выпуске финансовой миграции. Откат публичности бакета не должен быть автоматическим: он снова откроет скрытые изображения.
